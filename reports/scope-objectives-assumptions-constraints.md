# University Library Management System: Scope, Objectives, Assumptions and Constraints

## Purpose of This Document
This document explains the scope, goals, assumptions and limits of the University Library Management System (LMS) project. It covers the whole project and will be updated as the work moves forward.

## 1. Scope

### 1.1 Project Scope (overall)
A university library keeps records of books, borrowing, returns, students and overdue books by hand or with an old system. The team will plan a new Library Management System (LMS) that will handle:

- Books and book copies
- Library members
- Borrowing books
- Returning books
- Reservations
- Alerts for overdue books

The team will work like a real software team. It will plan the work, study the problem, write the requirements, draw diagrams, design a screen prototype, and keep all its work on Git and GitHub. The team does not need to build the full working system.

### 1.2 Project Activities
The team will do these tasks:

- Set up the repository and plan the project: README, schedule (Gantt chart), task list (WBS), who does what (responsibility assignment matrix), time estimates and risks
- Study the people who use the library and write the requirements, with user stories and acceptance criteria
- Draw UML diagrams: use case, class, sequence and activity diagrams
- Make a clickable prototype of the screens
- Work together on GitHub with Issues and clear commits

### 1.3 Intended Users of the LMS
- **Students:** search for books, see book details and reserve books.
- **Librarians:** manage book records, give out books, take returns and check overdue books.
- **Faculty members:** search for and borrow books.
- **Administrators:** manage library information and watch over the system.

### 1.4 Out of Scope
- Building the full working software.
- Extra features like online payment, barcode scanning and mobile apps, unless they are needed later.

## 2. Objectives

### 2.1 Project Objectives
- Plan a Library Management System that makes it easier to manage books, members, borrowing, returns, reservations and overdue books.
- Reduce manual work, save time and make records more correct.
- Make book search faster, keep records in order and spot overdue books easily.
- Practise using Git and GitHub and working as a team.

### 2.2 Project Deliverables
- A GitHub repository named university-library-management-system with the folders requirements, diagrams, ui-prototype and reports
- A README that explains the project, its goals, scope and team members
- A Gantt chart, schedule, task list (WBS), responsibility assignment matrix and time estimates
- A list of risks, with how likely each one is, how big its effect is and how to reduce it
- A requirements document with user stories and acceptance criteria
- UML diagrams and a clickable screen prototype
- GitHub Issues for each big task and clear commits that show progress

## 3. Assumptions
- All three team members have GitHub accounts, computers and internet when needed.
- Every member will take part, talk to the others and finish his tasks.
- Team members will use Git and GitHub, or learn them during the project.
- The university will give the project requirements and deadlines.
- Library staff can give correct information about books, copies, members, borrowing time and library rules when we need it.

## 4. Constraints
- **Time:** time is limited. The team must finish each part before the deadline set by the teacher. The work is shared among three members.
- **Tools:** Git and GitHub must be used to track changes, work together, see the commit history and manage tasks. Other tools can be used only if they help and the teacher allows them.
- **Team:** there are three members. Work is shared by responsibility, skill and estimated effort, and everyone keeps his work in the same GitHub repository.
- **Project limit:** the team must not build the full working system. The project focuses on planning, study, diagrams and the screen prototype.

## Conclusion
This document sets the limits of the University Library Management System project. It gives the team a clear base for planning, requirements, diagrams and the prototype, and it will be updated as the project grows.
